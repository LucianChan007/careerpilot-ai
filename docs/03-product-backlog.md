# CareerPilot AI Product Backlog

**项目名称：** CareerPilot AI  
**文档版本：** v0.1  
**研究依据：** Sprint 0 用户访谈，5 名真实大学生  
**估算方法：** Fibonacci Story Point（1 / 2 / 3 / 5 / 8）  
**优先级定义：**
- **P0：** MVP 核心能力，没有它就无法验证核心价值
- **P1：** 重要增强能力，MVP 可在核心闭环稳定后实现
- **P2：** 后续验证需求，暂不进入首个 MVP

# 2. 详细 User Story

## US01：上传简历并生成个人求职画像

**User Story**

> 作为一名求职大学生，我希望上传自己的简历后自动形成个人求职画像，从而避免每次使用 AI 都重复描述自己的背景。

**验收标准**

1. 用户能够上传 PDF/DOCX 格式简历。
2. 系统能够识别教育经历、技能、项目经历、实习经历等主要信息。
3. 系统生成结构化求职画像。
4. 用户能够查看生成结果。
5. 解析失败时，系统能够明确提示用户。

**优先级：** P0  
**Story Point：** 5  
**来源：** U02、U05

---

## US02：查看并修改个人求职画像

**User Story**

> 作为一名求职大学生，我希望修改 AI 自动生成的个人画像，从而纠正 AI 解析错误并补充我希望强调的信息。

**验收标准**

1. 用户可以修改技能、项目经历、求职方向等字段。
2. 修改后的内容可以保存。
3. 后续岗位分析使用最新画像。
4. 用户能够恢复或重新编辑信息。

**优先级：** P0  
**Story Point：** 3  
**来源：** 根据简历解析需求延伸

---

## US03：输入/上传 JD 并结构化解析

**User Story**

> 作为一名求职大学生，我希望输入或上传岗位 JD 后自动提取岗位要求，从而快速理解岗位内容。

**验收标准**

1. 用户可以粘贴 JD 文本。
2. 系统提取岗位名称、职责、技能要求、学历要求等信息。
3. 结果以结构化方式展示。
4. 无法识别的信息不会被系统伪造。

**优先级：** P0  
**Story Point：** 5  
**来源：** U01、U02、U04、U05

---

## US04：检查岗位硬性条件匹配情况

**User Story**

> 作为一名求职大学生，我希望快速知道自己是否满足岗位硬性要求，从而减少不合适岗位的时间成本。

**验收标准**

1. 系统能够逐项列出主要硬性条件。
2. 每项条件显示“满足 / 不满足 / 无法判断”。
3. 每项结论能够引用用户画像或 JD 中的对应依据。
4. 对无法判断的条件明确标注，不直接下结论。

**优先级：** P0  
**Story Point：** 3  
**来源：** U01、U02

---

## US05：分析技能匹配程度

**User Story**

> 作为一名求职大学生，我希望看到我的技能与岗位要求之间的匹配关系，从而判断是否值得投递。

**验收标准**

1. 系统提取 JD 中核心技能要求。
2. 将技能分为“已具备 / 部分具备 / 暂缺 / 无法判断”。
3. 每项技能给出判断依据。
4. 用户能够看到重点短板。

**优先级：** P0  
**Story Point：** 5  
**来源：** U02、U03、U04、U05

---

## US06：分析项目/经历与岗位匹配程度

**User Story**

> 作为一名求职大学生，我希望知道我的项目和经历与岗位工作内容是否相关，从而判断我的经历应该如何使用。

**验收标准**

1. 系统识别岗位主要工作内容。
2. 匹配用户项目、实习或工作经历。
3. 显示相关经历及对应关系。
4. 如果不存在明显相关经历，应明确说明。

**优先级：** P0  
**Story Point：** 5  
**来源：** U01、U04、U05

---

## US07：给出可解释的岗位匹配结论

**User Story**

> 作为一名求职大学生，我希望 AI 不只是告诉我“匹配度是多少”，还解释为什么，从而帮助我理解投递决策。

**验收标准**

1. 系统给出整体匹配结论。
2. 结论至少包含优势、短板和关键判断依据。
3. 不使用没有数据依据的“Offer 概率”冒充客观预测。
4. 用户可以继续追问具体判断依据。

**优先级：** P0  
**Story Point：** 3  
**来源：** U01、U02、U05

---

## US08：分析能力 Gap 并给出补强建议

**User Story**

> 作为一名求职大学生，我希望知道岗位要求和我当前能力之间的差距，从而知道面试前应该补什么。

**验收标准**

1. 系统列出岗位关键能力要求。
2. 标识用户当前不足。
3. 对主要 Gap 给出补强建议。
4. 建议与目标岗位直接相关。

**优先级：** P0  
**Story Point：** 5  
**来源：** U04、U05

---

## US09：根据 JD 生成针对性的简历修改建议

**User Story**

> 作为一名求职大学生，我希望 AI 根据具体岗位给出简历修改建议，从而突出与岗位最相关的经历。

**验收标准**

1. 系统同时读取用户画像和岗位 JD。
2. 指出建议重点突出的技能/经历。
3. 指出建议弱化或删除的低相关内容。
4. 能给出具体修改示例。
5. 不虚构用户不存在的经历或能力。

**优先级：** P0  
**Story Point：** 5  
**来源：** U01、U02、U03、U04、U05

---

## US10：基于简历和 JD 生成面试题

**User Story**

> 作为一名求职大学生，我希望 AI 根据岗位要求和我的个人经历生成面试问题，从而减少盲目准备。

**验收标准**

1. 面试题与 JD 有明确关联。
2. 面试题覆盖专业/技术、项目经历等类型。
3. 能结合用户个人经历生成追问。
4. 用户能够开始模拟面试。

**优先级：** P0  
**Story Point：** 3  
**来源：** U02、U05

---

## US11：进行多轮 AI 模拟面试

**User Story**

> 作为一名求职大学生，我希望 AI 扮演面试官进行多轮提问，从而在正式面试前进行模拟。

**验收标准**

1. AI 根据目标岗位开始面试。
2. 用户回答后 AI 可以继续追问。
3. 问题可以根据前一轮回答动态调整。
4. 用户可以结束本次模拟面试。

**优先级：** P0  
**Story Point：** 5  
**来源：** U02、U05

## US12：根据面试回答提供针对性反馈

**User Story**

> 作为一名求职大学生，我希望 AI 分析我的面试回答，从而知道具体应该如何改进。

**验收标准**

1. 系统指出回答中的主要问题。
2. 反馈结合目标岗位。
3. 给出具体改进方向。
4. 用户能够看到改进后的示例表达。
5. 反馈明确为辅助建议，不声称准确预测 Offer。

**优先级：** P0  
**Story Point：** 5  
**来源：** U02、U05

---

## US13：分析岗位实际工作内容与能力要求

**User Story**

> 作为一名求职大学生，我希望 AI 将 JD 转化为更容易理解的实际工作内容，从而降低 JD 描述模糊带来的判断成本。

**验收标准**

1. AI 能总结 JD 的核心工作内容。
2. 能说明岗位主要使用的技能和能力。
3. 对 JD 中不明确的信息明确标记。
4. 不将推测内容伪装成企业官方信息。

**优先级：** P1  
**Story Point：** 5  
**来源：** U01、U04

---

## US14：分析岗位发展方向并辅助判断

**User Story**

> 作为一名求职大学生，我希望了解一个岗位可能的发展方向，从而结合自己的职业规划判断是否值得投入时间。

**验收标准**

1. 系统根据岗位公开信息分析岗位发展方向。
2. 明确区分事实信息和 AI 分析。
3. 结合用户个人发展方向进行解释。
4. 对证据不足的内容标记不确定性。

**优先级：** P1  
**Story Point：** 5  
**来源：** U05

**验收标准**

1. 系统读取用户画像和求职偏好。
2. 能根据用户提供的岗位数据进行筛选。
3. 推荐结果给出推荐依据。

## US16：多个岗位横向比较

**User Story**

> 作为一名求职大学生，我希望同时比较多个岗位，从而在岗位选择时更容易做取舍。

**验收标准**

1. 用户可以选择至少 2 个岗位。
2. 系统从统一维度进行比较。
3. 至少包含技能匹配、经历匹配和岗位要求等维度。
4. 输出差异说明，而不是只给一个没有依据的总分。

**优先级：** P1  
**Story Point：** 5  
**来源：** 由岗位匹配与岗位取舍需求归纳

## US17：记录岗位收藏、投递和面试状态

# 3. MVP 建议

第一版 MVP 不建议一次实现全部 22 条 User Story。

建议以以下闭环作为首个可用版本：

**US01 → US03 → US04 → US05 → US06 → US07 → US08 → US09 → US10 → US11 → US12**

形成：

**简历 → JD → 岗位分析 → 匹配 → Gap → 简历优化 → 面试题 → 模拟面试 → 面试反馈**

这条链路能够直接验证 CareerPilot AI 的核心价值。

第一版暂时不依赖：

- 全网招聘网站爬虫
- 自动登录招聘平台
- 自动批量投递
- Offer 概率预测
- 复杂长期记忆系统

# 4. Backlog 优先级规则

后续新增需求时遵循：

**P0**

直接影响核心用户价值，或者没有该功能就无法完成 MVP 闭环。

**P1**

可以显著提高产品价值，但不影响第一版核心闭环。

**P2**

目前缺乏充分用户证据，或者属于增强型体验，应通过后续 Sprint 和真实用户反馈决定是否实现。

优先级可以在 Sprint Review 后调整，不能因为第一次规划写了 P0 就永远锁死。

---

# 5. Story Point 估算规则

采用 Fibonacci 估算：

| Story Point | 含义 |
|---:|---|
| 1 | 非常简单，基本不涉及复杂逻辑 |
| 2 | 简单功能 |
| 3 | 中等复杂度 |
| 5 | 较复杂，需要多个模块协作 |
| 8 | 复杂、存在较大不确定性，应考虑进一步拆分 |

Story Point 不等于“开发小时数”，用于比较相对工作量和 Sprint 容量。

# 8. Backlog 使用原则

本 Backlog 是 **Product Backlog 初始版本**，不是最终需求清单。

后续每一次用户测试、Sprint Review 和 Retrospective 都可能：

- 新增 User Story
- 删除 User Story
- 调整优先级
- 拆分 User Story
- 合并 User Story
- 重新估算 Story Point

需求变化必须在飞书中留下记录，以便最终项目汇报时展示“用户反馈 → Backlog 调整 → Sprint 迭代”的完整过程。
